Design goals

  1. 01 {{ partial "icon.html" "tick" }}

    Small enough to understand completely

    No framework soup. One Sass vocabulary, a few React islands, a tiny Go API. You can read the whole thing in an afternoon.

  2. 02 {{ partial "icon.html" "split" }}

    Two surfaces, one system

    Customer-facing pages for marketing, plus a small internal dashboard. Same tokens and BEM classes on both.

  3. 03 {{ partial "icon.html" "island" }}

    Separation of concerns

    Hugo owns documents, React owns interactive regions, Go owns data. Each layer has a job and a test suite.

  4. 04 {{ partial "icon.html" "git" }}

    Git-friendly increments

    Conventional commits, phase branches, green main at every step. The history is part of the demonstration.

The stack

Three runtimes, one class vocabulary, no CSS framework and no HTTP framework. Then the tools that persist, prove and ship it.

{{ partial "icon.html" "document" }}

Hugo Extended

Documents, Dart Sass, and the esbuild island pipeline. Marketing pages ship with zero JavaScript.

{{ partial "icon.html" "island" }}

React + TypeScript

Islands on audit, compare, result and dashboard. Vitest and Testing Library cover the interactive paths.

{{ partial "icon.html" "api" }}

Go net/http

Validate, fetch, score, recommend, persist. SQLite or memory behind a Repository. Optional dashboard password.

  1. Dart Sass + BEM

    One class vocabulary shared by Hugo and React. Autoprefixer on the production CSS. No Tailwind.

  2. SQLite

    modernc.org/sqlite so CGO_ENABLED=0 still builds. An empty -db stays in memory for tests and demos.

  3. Vitest + Go test

    Typecheck, coverage, go vet and the race detector. HTML fetch uses httptest fixtures — CI never needs the network.

  4. Docker

    Multi-stage image: Hugo public/ plus a distroless Go binary. One process serves the site and the API.

  5. Fly.io

    London region, HTTPS, autostop machines. A volume at /data keeps SQLite across deploys.

  6. GitHub Actions

    Go, frontend and Hugo jobs on every push. Green on main deploys with flyctl.

What it is not

The limits are deliberate. This is a demonstration of architecture, not a production auditor.

  1. 01

    Not Lighthouse, not RUM

    Scores come from one live HTML GET and table-driven signals. No JS execution, no Core Web Vitals, no real-user monitoring.

  2. 02

    Not a full crawl

    A single document, 10s timeout, 2 MiB cap. Authenticated or heavily client-rendered pages will look incomplete.

  3. 03

    Not a product backend

    The dashboard password is optional. History lives in memory or SQLite. Auth is an HMAC cookie, off by default for local demos.
